# 用户视角审查报告

> 审查目标：从"使用本平台的人"角度（包括最终业务用户、二次开发集成者、部署运维者、新接手的维护者），找出所有**容易引起误解、命名不明确、设计不一致、会让用户走弯路**的地方。
>
> 审查方式：只读审查，未修改任何业务代码。结论均附 `文件:行号` 证据，可逐条复核。
>
> 审查日期：2026-07-24
>
> 严重程度定义：
> - **P0 致命**：功能完全不可用，或存在安全漏洞，用户必然踩坑。
> - **P1 高**：大面积不一致，调用方无法凭直觉使用，维护必然出错。
> - **P2 中**：命名/体验/文档不一致，增加理解成本，偶发误用。
> - **P3 低**：仓库卫生、冗余、观感问题。

## 二、配置与部署（最容易让部署者误解）

### 2.1 默认数据库密码硬编码个人值且多处不一致 【P0】

- `workflow-server/workflow-app/src/main/resources/application.yml:17`
  ```yaml
  password: ${DB_PASSWORD:zhoudawei}
  ```
- `.env.example:5` 默认 `DB_PASSWORD=workflow`
- `docker-compose.yml:6,28` 默认 `${DB_PASSWORD:-workflow}`

**用户影响**：
1. 仓库中提交了开发者个人密码 `zhoudawei`，属于凭据泄露。
2. 本地直接 `java -jar` 启动（不读 `.env`）会用 `zhoudawei` 连库，必然失败；而 docker 启动用 `workflow`。三套默认值让部署者完全不知道该设什么。

### 2.2 文件存储路径默认值硬编码开发者本机绝对路径 【P0】

- `application.yml:80-81`
  ```yaml
  path: ${FILE_STORAGE_PATH:/Users/dawei/Documents/ddup/ai/flow/uploads}
  access-url: ${FILE_STORAGE_ACCESS_URL:/Users/dawei/Documents/ddup/ai/flow/uploads}
  ```
- `access-url` 的语义应是**对外可访问的 URL 前缀**（`.env.example:10` 写 `/uploads`），却默认成本机文件系统绝对路径。用户不设环境变量时，上传后返回的文件访问 URL 会是一个本地磁盘路径，前端无法访问。

**用户影响**：克隆后未配置环境变量直接启动，文件上传/预览功能异常，且暴露开发者本机目录结构。

### 2.3 JDK 版本三处矛盾 【P0】

| 来源 | 版本 |
|---|---|
| `README.md:7` | Java 17 |
| `workflow-server/pom.xml:35` `<java.version>` | 17 |
| `start.sh:13,23` | JDK 17 |
| `docs/deployment.md:5` | **JDK 21** |

**用户影响**：部署者读 `deployment.md` 装 JDK 21，但 pom 声明 17，构建行为不可预期；Dockerfile 用 21 构建、pom target 17，存在「构建 JDK 与目标字节码版本不一致」的隐患。三份权威文档（README/deployment/Dockerfile）说法不一，用户无法判断正确版本。

### 2.4 Flyway 基线配置与文档矛盾 【P1】

- `application.yml:28-29`：`baseline-on-migrate: true` + `baseline-version: "003"`
- `README.md:59`、`CONTRIBUTING.md:62`：声称基线是 `V001__business_schema.sql` / `V002__seed_builtin_data.sql`

**用户影响**：`baseline-version: "003"` 意味着对非空库做基线化时会跳过 V001/V002。文档却说 V001 是业务基线、V002 是种子数据。干净部署时 V002 种子数据到底有没有执行？文档与配置无法自洽，部署者无法预期初始数据状态。另：实际并无 `V002__seed_builtin_data.sql`（实际是 `V002__add_field_code_to_entity_form_field.sql`），文档与文件名也对不上。

### 2.5 生产不安全的默认配置 【P2】

- `application.yml:54` `flowable.database-schema-update: true`（默认允许引擎自动改表结构，生产风险）
- `application.yml:65` `com.workflow: DEBUG`（生产日志噪声与性能开销）
- `.env.example:8` 也默认 `FLOWABLE_SCHEMA_UPDATE=true`

**用户影响**：项目无 `application-prod.yml` 区分环境，部署文档未提示这些项在生产应关闭。用户按默认配置上生产会埋坑。

### 2.6 测试环境 application.yml 配了无效的 JPA 【P2】

- `workflow-server/workflow-app/src/test/resources/application.yml:12-15`
  ```yaml
  spring:
    jpa:
      hibernate:
        ddl-auto: create-drop
      show-sql: true
  ```
- 项目技术栈是 MyBatis-Plus（`README.md:7`、`application.yml:38`），根本未引入 JPA。

**用户影响**：测试配置里出现 JPA 配置，会让维护者误以为项目用了 JPA 做 ddl 生成，实际该配置无效（除非有 starter 恰好引入，但与声明技术栈矛盾）。

### 2.7 Docker 部署链路不透明 【P2】

- `docker-compose.yml` 中 `server` 服务**无 healthcheck**，`web` 仅 `depends_on: server`（无条件顺序）。
- `workflow-web/Dockerfile:9` 用 nginx 托管，但 docker-compose 未说明 nginx 如何把 `/api` 反代到 `server`，`nginx.conf` 也未在仓库可见位置（Dockerfile 引用 `nginx.conf`，需确认是否提交）。
- `docker-compose.yml:30` server 暴露 `SERVER_PORT: 8080`，但 `.env.example`/README 均未说明前端容器如何获得后端地址。

**用户影响**：按 `deployment.md` 执行 `docker compose up` 后，前端容器能否正确连到后端、何时启动，对部署者是个黑盒。

### 2.8 start.sh 硬编码开发者本机 Java 路径 【P3】

- `start.sh:14`
  ```bash
  DEFAULT_JAVA_HOME=/Users/dawei/Library/Java/JavaVirtualMachines/temurin-17.0.11/Contents/Home
  ```
- 虽有 `JAVA_HOME` 优先 + 存在性判断的 fallback，但把个人绝对路径写进脚本，对其他用户是噪音且暴露个人环境。

## 三、后端 API 设计（让集成开发者误解）

### 3.1 接口命名规范只规范了 4 个路径 【P1】

- `README.md:61-68` 声明 4 个"最终规范名称"（`/api/process-actions` 等）采用**复数+连字符**约定，并称"项目尚未正式上线，不保留旧接口兼容层"。
- 经核对，这 4 个路径在代码中字面一致（`FlowActionController.java:19`、`FlowActionHandlerController.java:23`、`FlowActionExecutionController.java:22`、`EntityFlowStatusController.java:15`）。

**但**：这 4 个"规范"控制器**自身的响应包装都不统一**——2 个用 `ApiResponse`、2 个用 `Result`。规范只管了路径，没管响应结构与 HTTP 语义。且全项目其余 40+ 接口几乎全用**单数**，与"规范"的复数约定相悖。开发者按 README 推断"新接口用复数"会和存量接口冲突。

### 3.2 单复数全局混用 【P1】

- **复数**（少数）：`/api/process-actions`、`/api/entity-forms/{formId}/nodes`、`/api/entity-lists`、`/api/entity-list-scopes`、`/api/ui-extensions`、`/api/ui-data-sources`、`/api/ui-component-templates`、`/api/tasks/{taskId}/...`
- **单数**（多数，约 30 处）：`/api/process`、`/api/process-instance`、`/api/process-task`、`/api/task`、`/api/entity`、`/api/entity-form`、`/api/entity-data`、`/api/entity-list-config`、`/api/file` 等

同一概念"任务"既有 `/api/task` 又有 `/api/tasks`；"表单" CRUD 用单数 `/api/entity-form`，其节点和发布却用复数 `/api/entity-forms`。调用方无法凭直觉推断路径。

### 3.3 "process-"/"entity-" 前缀与所属模块/功能域错位 【P2】

- `EntityFlowStatusController` 位于 workflow-entity 模块，路径却是 `/api/process-entity-status-mappings`（`EntityFlowStatusController.java:15`）。
- `ProcessNodeFormController` 位于 workflow-process，路径 `/api/process-node-form`；`EntityFormResolveController` 位于 workflow-process，路径 `/api/entity-form-resolve`。
- `SysMenuController` 位于 **workflow-entity** 模块，路径 `/api/system/menu`，但 `README.md:28` 声明"菜单"属于 workflow-system。

**用户影响**：按路径前缀定位代码、按 README 模块说明找文件都会扑空。

### 3.4 删除接口 4 种风格并存 【P1】

| 风格 | 示例 | 位置 |
|---|---|---|
| `POST /{id}/delete`（主流） | 系统模块、EntityForm、ProcessDefinition | `SysUserController.java:81` 等 15+ 处 |
| `POST /delete/{id}`（动词前置，与上相反） | EntityStatus、EntityListConfig | `EntityStatusController.java:60`、`EntityListConfigController.java:209` |
| 裸 `POST /{id}` 即删除 | NodeConfig、ProcessNodeForm、FlowAction | `NodeConfigController.java:70`、`FlowActionController.java:104` |
| 裸 `POST /`（集合根）即删除 | File | `FileController.java:81` |

**用户影响**：`POST /api/file` 看起来像"创建文件"实为删除；无统一约定，前端拼 URL 必须逐个查。

### 3.5 裸 `POST /{id}` 语义相反（最危险的歧义）【P1】

相同路径形态 `POST /{resource}/{id}` 在不同 Controller 里含义完全相反：

| Controller | `POST /{id}` 含义 | 位置 |
|---|---|---|
| NodeConfigController | **删除** | `NodeConfigController.java:70` |
| ProcessNodeFormController | **删除** | `ProcessNodeFormController.java:53` |
| FlowActionController | **删除** | `FlowActionController.java:104` |
| UiExtensionDefinitionController | **更新**（`service.save`） | `UiExtensionDefinitionController.java:69` |
| EntityListConfigController | **局部 patch** | `EntityListConfigController.java:100` |

**用户影响**：拿到一个 `POST /xxx/{id}` 接口，无法判断它是删、是改、还是补丁。误调会把数据删掉。

### 3.6 两套"统一响应"包装并存且同控制器内混用 【P1】

- `Result<T>`（`workflow-common/src/main/java/com/workflow/common/Result.java:11`，字段 `code/message/data`，Javadoc 自称"统一响应结果"）
- `ApiResponse<T>`（`workflow-common/src/main/java/com/workflow/dto/ApiResponse.java:15`，字段 `code/message/errorCode/data`，Javadoc 自称"统一API响应包装类"）
- `ProcessInstanceController` **同一控制器 6 个方法交替使用两种**：`getProcessProgress` 返 `ApiResponse`(:37)、`getProcessDetail` 返 `Result`(:48)、`getMyStartedList` 返 `Result`(:61)、`terminateProcess` 返 `Result`(:83)、`getProcessXml` 返 `Result`(:105)、`triggerReceiveTask` 返 `ApiResponse`(:118)。
- `GlobalExceptionHandler` 统一返回 `ApiResponse`。于是对声明返回 `Result` 的 Controller，**成功响应是 `Result` 结构、错误响应是 `ApiResponse` 结构**，同一端点 envelope 不稳定。

**用户影响**：前端需写两套解析；调用方无法靠响应结构稳定判断。

### 3.7 任务域 4 个 Controller 三重重复 【P1】

| 动作 | 3 处实现 |
|---|---|
| `complete` | `TaskController.java:61`、`TaskActionController.java:34`、`ProcessTaskController.java:158` |
| `withdraw` | `TaskController.java:85`、`TaskActionController.java:71`、`ProcessTaskController.java:214` |
| `history` | `TaskController.java:96`、`TaskActionController.java:96`、`ProcessTaskController.java:200` |
| `statistics` | `TaskController.java:27`、`TaskActionController.java:112`、`ProcessTaskController.java:140` |

加上 `TaskOperationController`（`/api/tasks/{taskId}/...`），共 4 个 task 控制器，路径前缀 `/api/task`、`/api/task-action`、`/api/process-task`、`/api/tasks` 全不同。且实现逻辑不一致（`TaskController.completeTask` 不带 formData，`ProcessTaskController.completeTask` 带 formData，`TaskActionController` 走加签分支）。

**用户影响**：调用方完全不知道"完成任务"该调哪一个；维护改一处漏两处是必然结果。

### 3.8 HTTP 状态码语义混乱 【P1】

- `GlobalExceptionHandler` 中 `BusinessConflictException`→409、`ForbiddenException`→403、`IllegalArgumentException`→400、`NoResourceFoundException`→404（均用 `ResponseEntity` 设状态码）；但 `handleRuntimeException`(:158)、`handleSQLException`(:167)、`handleException`(:176)、`handleDuplicateKeyException`(:104) **直接返回 `ApiResponse`（无 `ResponseEntity`）→ HTTP 200**，仅 body 写 `code:500`。
- 8 处 `throw new RuntimeException("status参数不能为空")`（如 `SysUserController.java:101`、`SysRoleController.java:112` 等），本是参数错误应 400，却变成 200/500。
- 多个 Controller 手动 `catch(Exception){ return Result.error(500,...) }` 绕过全局处理器（`TaskActionController.java:59,86,103,123`、`ProcessTaskController.java:151,193,206,231`、`AuthController.java:47,52,70`）。最严重：`TaskActionController` 的 `catch(Exception)` 会把 `ForbiddenException`（应 403）也吞成 `Result.error(500,...)`。
- **登录失败返回 HTTP 200**（`AuthController.java:47,52,70`），认证失败本应 401。

**用户影响**：客户端无法靠 HTTP 状态码可靠判断成败，必须读 body.code；前端按 401 跳登录的逻辑失效。

### 3.9 POST 语义不统一（创建 vs upsert）【P2】

- 纯创建：`SysUserController` `POST /`(:57) + `POST /{id}/update`(:69)
- upsert 不区分：`EntityListConfigController` `POST /save`(:74)、`UiComponentTemplateController` `POST /`(:53) 注释明说"新增或更新"、`EntityCodeRuleController` `POST /`(:31)
- 三种写法（`POST /`、`POST /save`、`POST /{id}/update`）并存，调用方无法预期 `POST /` 是创建还是 upsert。

### 3.10 读操作用 POST 且与 GET 重叠 【P2】

- `EntityDataController` 既有 `GET /entity/{entityCode}`(:37) 又有 `POST .../search`(:214) 做同类条件查询。
- `UiDataSourceController` `POST /{id}/preview`(:115) 注释标"不产生副作用"本应是 GET 语义。
- `EntityDataController` `POST .../export`(:238)、`ConfigMigrationController` `POST /packages/export`(:96) 导出（读）用 POST。

**用户影响**：读操作用 POST 破坏缓存/幂等语义，且与同控制器 GET 查询重叠，调用方不知该用哪个。

### 3.11 缺少校验异常处理器 【P2】

- `GlobalExceptionHandler` 无 `MethodArgumentNotValidException`/`ConstraintViolationException`/`BindException` 的 `@ExceptionHandler`。
- 控制器大量用 `@Validated`/`@Valid`（`SysUserController.java:58`、`AuthController.java:43`、`FlowActionController.java:97`）。校验失败落到 `handleException`(:176) 返回 HTTP 200 + "系统繁忙"，把"字段必填"等用户错误误报成系统故障，拿不到具体校验信息。

### 3.12 其它卫生问题 【P3】

- `UiConfigReleaseController.java:26` 类级 `@RequestMapping("/api")`，把资源名全放方法级，与其余所有控制器"类级声明资源名"的约定不一致。
- `EntityListConfigController.java:87-91` 残留 `@Deprecated` public 方法无映射，注释称"保留给既有直接调用测试的兼容入口"，属死代码。
- 18 个 Controller 冗余标注 `@CrossOrigin(origins="*")`（如 `AuthController.java:28`），而全局 `CorsConfig` 已配置 `/**`，功能冗余但表明 CORS 策略来源混乱。

## 四、前端交互（让最终用户与二次开发者误解）

### 4.1 三处功能完全不可用 【P0】

详见 §一 5/6/7。此处补充影响：

- **组织/部门更新删除 405**：`Organization.vue:245,268` 调 `POST /system/org/{id}`，后端 `SysOrganizationController.java:75,87` 只有 `/{id}/update`、`/{id}/delete`。用户点"编辑/删除组织"必失败。且 `api/system/org.ts` 只有 2 个只读方法，CRUD 缺失。
- **文件删除参数错位**：`file.js:45` `request.post('/file', { params: { url } })` 把 axios config 当 body。后端 `FileController.java:81-82` 期望 `?url=` query。删除附件始终失败。
- **角色/用户组新建空 body**：`Role.vue:283`/`Group.vue:248` 调 `createX(formData.id, formData)`，但 `createRole/createGroup` 签名是 `(data)`，实际提交空串。新建不可用。（对比 `Menu.vue:644` 用显式 if/else 传参，正确。）

### 4.2 登录 admin/admin 后门 【P0 安全】

- `AuthController.java:56-64` 对 `username=admin&password=admin` 直接放行并自动落库加密密码。
- `Login.vue:55` 登录页明文展示"默认账号: admin / admin"。

**用户影响**：生产环境弱口令后门；登录页公开展示默认凭据，误导用户以为是正式账号。

### 4.3 API 调用层风格分裂 【P2】

- 业务模块用"对象聚合"导出（`export const entityApi = {...}`，`src/api/entity.js:6` 等）。
- 系统模块用"独立具名函数"导出（`export const getUserList = () => {}`，`src/api/system/*.ts`）。
- `src/api` 下 `.js` 与 `.ts` 混存。
- `User.vue:191`、`Organization.vue:148` 还直接 `import request` 绕过 API 层。

**用户影响**：二次开发者导入方式不统一（`import { entityApi }` vs `import { getUserList }`），心智负担大。

### 4.4 同一域两套路径前缀（entity-form vs entity-forms）【P2】
