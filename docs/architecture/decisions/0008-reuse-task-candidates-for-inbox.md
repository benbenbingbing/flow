# ADR-0008：复用任务候选表并建立列表摘要

- 状态：已实现，完成针对性验证；尚未应用到业务库
- 日期：2026-09-23
- 详细设计：[待办/已办列表最终方案](../task-inbox-query-design.md)

## 背景与证据

首页和移动端共用的已办接口先读取全部任务，逐条补充历史流程、用户和完整业务聚合，再在内存中过滤、分页。本地日志中的两次请求耗时为 2222 ms、2513 ms。

`process_task_candidate_user`、`process_task_candidate_group` 均有实体和 Mapper，但实施前生产源码未发现业务调用。V081 删除旧 `process_task_instance` 时保留了两张候选表。

2026-09-23 对项目 `.env` 指向的本地 MySQL `workflow` 库进行了只读检查：两表均存在、结构与 V001 一致、各 0 行、无外键；旧任务实例表不存在。该结果不代表其他部署环境。

## 决策

1. **复用两张候选表，不新建 `process_task_actor`。** 候选用户、组和角色是候选身份；实际办理人继续存于 `process_task.assignee_id`，不把全部候选人算作已办。
2. 将两表的 `task_instance_id` 明确调整为 `process_task_id bigint`，关联 `process_task.id`，保留唯一关系并补充用户/组到任务的反向索引。其他环境如有旧数据，先核实关联，禁止直接强转或清空。
3. 候选组不展开为每个成员。保留当前用户 ID/用户名、组 ID/编码以及 `ROLE_` 角色兼容规则，查询实时有效的组织成员关系。
4. 主表补充发起人身份和业务名称、编号、当前节点、状态等轻量摘要；业务摘要沿用当前记录的最新值口径，在业务变更事务中同步。表单 JSON、子表及完整聚合不进入列表查询。
5. 列表在数据库完成授权范围筛选、业务搜索、排序、分页和统计。普通待办保留轻量引擎运行任务关联，核对任务存活和当前认领状态；加签继续采用原有效性规则；提交仍实时校验引擎权限。
6. 统一身份投影服务覆盖创建后的最终分配、认领、转办、候选变更、异常分配修复、SLA、完成和取消等入口，与引擎事务一致。补偿同步必须能修复已有记录，不能“已存在即跳过”。

## 取舍

采用本地候选关系与任务摘要，可以使用普通关系查询和数据库分页，减少读取引擎历史及完整实体数据的开销。已有两张空表可复用，前端 API 可以保持不变。

代价是任务全部生命周期与摘要同步需要完整覆盖；最新业务值同步至历史任务会产生写放大和锁竞争，必须同时评估写入延迟。单纯增加索引或候选表不会自动解决逐条读取完整业务聚合的问题。

暂不采用新增统一 actor 表，也不将本地候选表升级为独立审批授权系统；组成员展开成用户明细会增加组织变更时的维护成本，因此不采用。

## 实施与验证

按“新增版本迁移 → 接入全部同步写入 → 分批幂等回填 → 新旧结果比较 → 配置切换分页读取”实施。实际新增迁移前重新检查最大版本，历史版本迁移不修改。保留原查询作为回切路径，不回滚业务数据。

验收必须覆盖候选与组角色变化、并发认领和转办、加签/撤回/取消、真实完成者、所有搜索字段与总数、事务回滚、重复事件及并发回填。配套修复移动端首屏重复请求，并将统计改为数据库聚合。

实现与验证见 [实施验收记录](../../testing/task-inbox-read-model-2026-09-23.md)。新增 V105 Java 迁移；历史迁移未修改或删除。业务库尚未应用本次升级。
