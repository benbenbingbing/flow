# Flow 生产级长时间压测执行方案

## 1. 目标与边界

本次测试用于回答四个问题：

1. 在目标业务峰值和预留余量下，系统能否连续运行超过 6 小时且没有性能漂移。
2. 应用、MySQL、Flowable、对象存储和异步队列中，哪个组件最先形成容量上限。
3. Pod 重建、扩缩容和观测后端异常时，核心业务是否保持可用并能自行恢复。
4. Metrics、Logs、Traces 和审计数据能否完整关联，是否足以定位超时、错误和堆积。

压测环境必须与生产版本、部署方式和关键参数一致，但使用隔离数据库、Bucket、
域名、凭据和通知接收端。测试允许写业务数据，不允许调用真实客户 Webhook、短信、
邮件、支付或其他不可逆外部系统。

“所有脚本执行成功”不等于生产容量结论。最终容量取应用、数据库、流程引擎、
对象存储、异步消费者和网络中最低的可持续值，并保留故障域余量。

## 2. 推荐拓扑

正式测试至少分离两个角色：

- 被测服务器：运行 k3s、Flow、MySQL、MinIO 和完整观测栈。
- 负载发生器：运行 k6 和外部健康探针。优先使用当前开发机或另一台服务器，避免
  k6 与被测业务竞争 CPU、内存、磁盘和 conntrack。

如果只能使用一台服务器，k6 必须设置独立 CPU/内存限制，并在报告中标注结果受
资源竞争影响，不作为最终容量上限。

被测服务器建议最低规格：

- 8 vCPU、16 GiB 内存；同时启用 SkyWalking 和 Elasticsearch 时建议 32 GiB。
- 200 GiB SSD，持续写入能力和 IOPS 可观测。
- Ubuntu 24.04 LTS，时间同步正常，文件描述符和 conntrack 容量经过检查。
- 公网只开放 SSH、HTTPS；Grafana、Prometheus、SkyWalking UI 通过 SSH 隧道或
  受认证 Ingress 访问，不直接裸露管理端口。

服务器实际规格不满足时，应缩小观测保留期或拆分组件，不能通过取消内存限制来
伪造稳定性。

## 3. 完整观测基线

正式压测开始前必须全部通过：

| 领域 | 组件与数据 | 必须验证 |
| --- | --- | --- |
| 应用指标 | Actuator、Micrometer、Prometheus | HTTP QPS/错误/p50/p95/p99、JVM、GC、线程、Hikari、队列 |
| 集群指标 | kube-state-metrics、node-exporter、metrics-server | Node/Pod CPU、内存、磁盘、网络、重启、调度、CPU throttling |
| 日志 | JSON 日志、Promtail、Loki | request/trace/business trace 关联、无敏感字段、采集积压可见 |
| Trace | 应用 OTel、OTel Collector、Tempo | 登录、查询、写入、MySQL、Flowable、异步链路可检索 |
| SkyWalking | OAP、Elasticsearch、UI | 服务、端点、拓扑和 Trace 可查询；停机不影响业务 |
| 展示 | Grafana | 指标到 Trace、日志到 Trace、Trace 到日志跳转有效 |
| 告警 | PrometheusRule、Alertmanager | 5xx、延迟、实例不足、队列堆积、磁盘、重启和采集缺失可触发 |

业务应用只向有界、短超时的 OTel Collector 出口发送遥测。Tempo、SkyWalking、
Prometheus、Loki、Grafana、Elasticsearch 或 Collector 中任一组件不可用时，不得
影响业务启动、readiness 或请求处理。

正式长稳期间至少保留 7 天 Prometheus 数据和覆盖测试窗口的 Loki、Tempo、
SkyWalking 数据。测试完成后再按容量和成本调整生产保留策略。

## 4. 数据和账号准备

准备三类数据集：

- 小数据集：验证单记录和小分页响应。
- 中数据集：每个核心实体至少 10 万条，用于分页、过滤、排序和权限范围查询。
- 热点数据集：少量高频实体、流程定义和字典，验证缓存、锁和热点行竞争。

准备专用账号池，至少覆盖：

- 普通用户、跨部门用户、管理员和只读用户。
- 不同数据范围和实体行级权限。
- 流程发起人、候选人、审批人和抄送人。
- 开放 API 客户端、Webhook 测试接收端和连接器测试目标。

账号和业务数据必须可追踪到运行批次。所有外部通知使用测试接收端，连接器只允许
访问白名单中的可控服务。

## 5. 场景矩阵

### 5.1 核心在线业务

- 登录、Token 刷新、当前用户和权限加载。
- 用户、用户组、组织和字典分页查询。
- 实体列表、筛选、排序、详情和行级权限。
- 实体创建、更新、状态变更和删除。
- 待办、已办、统计、详情、认领和审批。
- 流程发起、多人审批、驳回、重提、撤回、终止和历史查询。
- 文件上传、下载和删除，覆盖小文件、常规文件和允许的上限文件。
- 开放 API 鉴权、幂等请求、限流、查询和写入。

仓库脚本默认启用无需固定业务模型的通用场景。实体写入和完整流程审批必须在目标
实体、流程、审批人和数据权限准备完成后，通过外部 fixture 启用。不能使用随机
字段绕过真实校验。

### 5.2 后台与异步业务

- Outbox、系统审计、流程状态同步和 Webhook 队列在持续写入下的深度和最老年龄。
- Schema worker 发布任务的租约、幂等和故障接管。
- Webhook/Connector 的成功、超时、重试、死信和恢复排空。
- 日志、Trace 和指标采集队列在后端变慢时的有界丢弃。

### 5.3 数据分布

- 80% 常规查询、15% 复杂查询、5% 写入作为初始比例。
- 热点与冷数据、第一页与深分页、命中与未命中、允许与拒绝权限同时覆盖。
- 写入比例最终根据真实业务调整，不能为了提高 QPS 只压最轻的接口。

## 6. 执行批次

每个批次独立记录 Git SHA、镜像摘要、Helm revision、服务器规格、数据库参数、
数据规模、负载参数和时间窗口。

### 批次 A：部署和空载基线

- 全量测试、清单验证和 Helm test 通过。
- 空载观察 30 分钟，确认 Pod 无重启、日志无持续错误、队列为空、Trace 可查询。
- 记录 Node、Pod、JVM、MySQL、MinIO 和观测组件基线。

### 批次 B：2 分钟烟测

- 只读开始，验证认证、路由、权限、阈值和结果目录。
- 开启写入后验证测试数据前缀、完整清理和审计记录。
- 任一接口业务响应错误都必须先处理，不能带错进入长测。

### 批次 C：35 分钟基线

- 5 分钟预热、30 分钟目标基础负载。
- 确认负载发生器 CPU 小于 70%，无 dropped iterations。
- 根据吞吐和资源使用确定长稳基础到达率，不直接采用脚本默认值。

### 批次 D：6 小时 30 分钟长稳

- 15 分钟预热。
- 90 分钟稳态。
- 30 分钟业务峰值。
- 3 小时 45 分钟持续负载。
- 10 分钟突刺。
- 20 分钟恢复观察。

本批次不主动注入故障，目标是识别内存泄漏、连接泄漏、队列增长、日志/Trace
堆积、磁盘增长和延迟漂移。

### 批次 E：阶梯压力

- 逐级运行 1x、2x、4x 和目标极限负载，每级至少 10 分钟。
- 记录第一个违反 SLO 的组件和负载点。
- 达到终止条件后降回 1x，验证 20 分钟内恢复，不持续硬压已饱和系统。

### 批次 F：故障和恢复

在稳定 1x 业务流量下逐项执行，每次只注入一个故障并恢复：

1. 删除一个 server Pod，验证另一个副本承接且请求不中断。
2. 停止 schema worker，积累少量受控任务后恢复并验证只执行一次。
3. 停止 OTel Collector、Tempo、SkyWalking、Loki、Prometheus、Grafana 和
   Alertmanager，分别验证业务不受影响。
4. 对 MySQL、MinIO 和测试 Webhook 注入连接拒绝、超时和慢响应。
5. 重启一个 MySQL/MinIO Pod，验证错误明确、数据完整和恢复时间。
6. 模拟磁盘高水位、连接池耗尽和异步队列积压，验证告警和保护策略。

观测平台整体中断时仍需要独立 k6 结果、外部 `/livez` 探针和服务器系统日志作为
证据，避免用已经失效的监控证明业务可用。

## 7. 发布阈值

初始门禁如下，最终应按产品 SLO 调整：

- HTTP 失败率小于 0.5%，业务响应错误率小于 0.5%。
- 普通读取 p95 小于 750 ms，写入 p95 小于 1500 ms，总体 p99 小于 2500 ms。
- `/livez` 独立探针无失败，业务 Pod、MySQL 和对象存储无非计划重启。
- k6 `dropped_iterations` 为 0；负载发生器 CPU 小于 70%、内存稳定。
- 峰值结束 20 分钟内，延迟、线程、连接池和队列恢复到基线的 120% 以内。
- Hikari pending 连接持续为 0；数据库连接总量不超过 `max_connections` 的 80%。
- Old Gen、线程数、文件描述符、磁盘和活跃时间序列不存在持续单调增长。
- 任一业务或观测容器的内存工作集不超过容器限额的 90%；达到 90% 持续 5 分钟告警，达到 97% 持续 2 分钟升级为严重告警。
- Outbox/Webhook/动作队列最老年龄在恢复阶段归零，无重复非幂等副作用。
- OTel 队列不持续满载；Tempo 和 SkyWalking 能检索压测 Trace；日志可按 trace id
  回查且不含密码、Token、文件内容或完整业务载荷。
- 观测后端逐项停止时，业务成功率相对同期基线下降不超过 0.1%，p95 增幅不超过 5%。

## 8. 立即终止条件

满足任一条件应停止提升负载，并保留现场：

- 连续 2 分钟业务错误率超过 20% 或 `/livez` 连续失败。
- 数据错误、越权、重复审批、重复外部副作用或无法清理的业务数据。
- Node 内存压力、磁盘剩余小于 15%、持续 OOM、文件系统只读或数据库恢复异常。
- MySQL 连接接近上限、复制/持久化异常、锁等待持续增长或慢查询失控。
- k6 自身饱和导致大量 dropped iterations，无法证明负载按计划产生。

终止后不得立刻重启所有组件。先保存 k6、Prometheus、Loki、Tempo、SkyWalking、
Kubernetes events、应用线程/堆信息、MySQL 状态和服务器系统日志，再决定修复或恢复。

## 9. 问题处理闭环

每个问题单独记录：时间、阶段、负载、症状、受影响接口、Trace、相关日志、指标、
根因、代码或配置修改、回滚方式和复测结果。

修复流程：

1. 停止提升负载，保存证据并用最小场景复现。
2. 在功能分支修复，执行相关单元/集成测试和安全扫描。
3. 构建不可变镜像并记录摘要，使用 Helm 原子升级。
4. 先跑烟测，再跑触发问题的最小批次，最后重跑完整基线或长稳。
5. 不通过关闭告警、扩大无限队列、取消资源限制或吞掉异常来“修复”结果。

## 10. 最终报告

报告至少包含：

- 环境规格、拓扑、Git SHA、镜像摘要、Helm revision 和数据规模。
- 每阶段计划/实际到达率、HTTP 请求量、成功率、p50/p95/p99 和 dropped iterations。
- Node/Pod/JVM/GC/线程/Hikari/MySQL/MinIO/队列的峰值与趋势。
- Metrics、Logs、Tempo、SkyWalking 的关联样例和告警触发证据。
- 故障注入时间线、业务影响、检测时间、恢复时间和数据完整性结果。
- 所有发现问题、修复提交、复测批次和仍未消除的风险。
- 可持续容量、建议生产上限、自动扩缩容区间和至少 30% 的故障域余量。

只有当全部必选场景、阈值、数据清理、观测闭环和故障恢复均有证据时，才能将结果
标记为通过。单次 6 小时成功不能替代生产同规格环境的定期容量回归。
