# 流程用户范围：多级实体关系选择实现方案

日期：2026-10-14。状态：已实现并通过定向回归；数据库迁移文件已新增，尚未在现有业务数据库执行。

目标：将“实体用户关系字段”从单字段选择升级为逐级关系路径选择。例如：

```text
流程绑定记录 → 申请用户 → 所属部门 → 创建人
流程绑定记录 → 关联项目 → 业务部门 → 创建人
流程绑定记录 → 关联明细（多条） → 经办人
```

起点沿用当前语义：流程绑定实体的当前业务记录。“用户”可以是记录上的任意用户关系字段。若还需要直接从“流程发起人”开始，应作为明确的另一种起点扩展，不能默认使用当前登录用户，避免后台执行、转办和重试时结果变化。

## 1. 当前实现与实际缺口

| 位置 | 当前行为 | 所需变化 |
| --- | --- | --- |
| `workflow-web/src/components/NodeConfigPanel.vue` | 从绑定实体字段中过滤用户关系，使用 `el-select` 保存一个 `fieldCode` | 改为可逐级展开、可在用户节点结束的关系路径选择器 |
| `workflow-web/src/shared/process-config/index.js` | `schemaVersion: 1 + entityCode + fieldCode`；只按末端字段类型决定分配方式 | 新增路径契约，按整条路径计算单值/多值 |
| `EntityUserReferenceFieldConfig` / `EntityUserReferenceFieldPersonResolver` | V1 参数白名单，只校验与读取直接用户字段 | 兼容 V1，新增 V2 路径校验和运行时解析 |
| `EntityUserReferencePort` / `EntityUserReferenceAdapter` | 单字段读取，用户主键转换为用户名，最多 200 人 | 增加路径能力，保留现有身份转换规则 |
| `PublishedRelationPathResolver` | 支持发布快照、引用字段、实体关系、反向引用，路径最多 8 步 | 复用动态实体路径编译基础，补齐系统关系与旧类型兼容 |
| `EntityRelationGraphReadService` | 有批量投影、授权和预算控制；末层支持分页；禁止路径重复经过同一记录 | 人员解析必须取得完整结果，并允许有限路径再次经过同一用户 |
| `ConfigMigrationAssignmentSupport` | 只映射 `entityCode/fieldCode` | 逐段处理路径依赖和跨环境引用 |

两个不能忽略的限制：

1. 系统实体目录按数据库列类型登记字段。虽然 `SystemEntityFieldPolicy` 已识别 `dept_id`、`org_id`、`create_by` 等引用语义，但这不等于已具备可执行的关系路径；现有通用路径编译器也不能直接覆盖所有系统字段和历史 `USER` 类型。
2. 仓库中的 `sys_organization` 表及 `SysOrganization` 模型目前没有创建人字段。用户示例若指系统部门，必须增加创建人记录能力。不能将“负责人”当作“创建人”；负责人另有职务任职语义。

## 2. 选择交互与业务规则

新增可复用组件 `EntityUserRelationPathSelector.vue`，节点配置面板负责传入根实体和接收完整路径。

- 使用分栏级联选择，展开一层时再加载目标实体的关系元数据，避免预先递归加载整个实体图。
- 所有具有合法关系定义的节点都可以继续展开，包括单选引用、多选引用、显式实体关系和受支持的系统关系。反向引用必须有明确的来源字段与目标实体元数据，不能任意扫描数据库关联。
- 用户关系同时支持两种操作：“选为人员来源”和“继续展开”。例如可以停在“申请用户”，也可以继续到“申请用户 → 所属部门 → 创建人”。不要把用户节点固定为叶子。
- 最终必须落到 `sys_user` 或可规范化为系统用户的旧用户关系。部门、项目可以作为中间节点，普通文本、日期等不能作为人员来源。
- 回显完整面包屑及“单人/可能多人”；改变上游选择后清空下游路径。
- 原字段删除、关系失效或缺少发布版本时，保留已有路径并显示失效位置，禁止静默清空或替换。
- 深度最多 8 步，与现有路径基础一致；达到上限仍可选择当前用户节点，但不能继续展开。

关系选项由后端统一返回：稳定编码、名称、关系种类、目标实体编码、单/多值、可展开、可结束、不可用原因。设计器只消费这些能力，不按字段名称自行猜测关系。

## 3. 配置结构与兼容

沿用 `assigneeType: interface` 和 `resolverCode: entityUserReferenceField`，无需另起一套任务分配机制。人员参数增加 V2，外层现有 assignment 配置版本不变。

以下为拟议配置示例，`applicant` 是业务字段示意，`create_by` 为拟新增的部门创建人字段：

```json
{
  "assigneeType": "interface",
  "resolverCode": "entityUserReferenceField",
  "assignmentMode": "DIRECT",
  "extraParams": {
    "schemaVersion": 2,
    "entityCode": "expense",
    "path": [
      { "type": "REFERENCE_FIELD", "code": "applicant" },
      { "type": "SYSTEM_REFERENCE", "code": "dept_id" },
      { "type": "SYSTEM_REFERENCE", "code": "create_by" }
    ]
  }
}
```

路径存稳定编码，不存展示名称、SQL、表名或前端指定的物理列。普通引用目标由后端推导；需要显式目标的反向引用保存稳定目标实体编码，再由服务端定位本环境实体。

兼容要求：

- V1 的 `entityCode + fieldCode` 继续由原逻辑执行，保持已有运行中流程语义。
- 设计器可把 V1 显示为一段路径；没有编辑人员来源时保持原配置，编辑后才按 V2 保存。
- 解析器参数 schema 同时接受 V1/V2，分别严格校验，不能允许两种坐标混用。
- 保留现有 resolverCode，以便普通任务、多人办理、下一审批人候选范围继续使用统一入口。
- 更新扩展描述和目录中保存的 schema，避免界面接受新配置而发布或导入仍按 V1 拒绝。

## 4. 关系元数据、发布与运行时

### 4.1 统一关系元数据

在实体模块增加统一的关系元数据服务，设计期选项、发布校验和执行共同使用。流程模块仅通过 `workflow-port` 的稳定接口调用，不能直接依赖实体 Mapper。

动态实体基于已发布关系定义与字段元数据识别目标；现代引用优先使用真实 `refEntityId`。存在现代目标但目标失效时不能回退旧 `refEntityType`。历史 `USER`、`DEPT` 等字段按原有存储契约显式适配。

系统实体增加按“实体编码 + 字段编码”登记的关系白名单，例如：

| 来源 | 目标 | 含义 |
| --- | --- | --- |
| `sys_user.dept_id` | `sys_organization` | 用户所属部门 |
| `sys_user.org_id` | `sys_organization` | 用户所属组织 |
| `sys_organization.parent_id` | `sys_organization` | 上级组织部门；顶级哨兵值不当作记录 |
| `sys_organization.create_by`（新增） | `sys_user` | 创建该组织部门的用户 |

这些元数据由服务端定义并带版本，不能仅凭任意字符串字段叫 `create_by` 就赋予它用户关系语义。系统目录同步不能覆盖或丢失这层关系定义。

### 4.2 发布校验与编译

保存阶段校验路径结构并反馈具体失效步骤；发布阶段必须再次逐跳校验根实体绑定、关系存在性、发布状态、目标连续性、终点用户类型和分配模式。

V2 在发布时生成服务端执行描述，作为流程发布产物保存，描述包含动态实体精确发布版本及 schemaHash、系统关系契约版本和实际单/多值属性。执行描述不能信任浏览器传入值；运行时不使用最新草稿来解释已发布路径。

这里需要扩展现有发布产物和人员解析调用链，把服务端编译结果传给实体端口；不能仅在前端增加 path 字段。跨环境导入需重新绑定目标环境发布版本，不照搬源环境的 historyId 或实体数据库 ID。

### 4.3 运行时按步骤求值

1. 从可信流程上下文获取绑定实体和业务记录 ID，校验与配置一致。
2. 按已编译路径读取各层记录，单值形成一个目标，多值展开为集合。
3. 每层按“实体 + 记录 ID”去重并批量读取下一层；不能每个目标单独查询。
4. 最终用户按规范身份去重，转换为流程使用的 canonical username，复用已有用户状态过滤。
5. 把结果交回现有普通任务、候选人或多实例分配逻辑。

实体结构按发布版本解释，记录值按节点激活时最新持久化值读取。后续部门关系发生变化时影响尚未创建的任务，不反向重派已经创建的任务。下一审批人预览使用相同解析器，实际提交仍需复核。

身份转换要延续现有约束：现代用户引用按用户 ID 精确解释；旧 username 存储仅走明确的兼容分支。中间经过旧用户关系时，先规范化为 sys_user 主键再向下读取，避免 ID 与 username 同值时指向错误用户。

### 4.4 整条路径的单/多值语义

| 路径特征 | 普通任务 | 多人办理 |
| --- | --- | --- |
| 每一步均为单值 | `DIRECT` | 解析到的用户生成实例 |
| 任意一步可能为多值 | `CANDIDATE` | 去重后的全部用户分别生成实例 |

例如“多个项目 → 每个项目的单选负责人”仍是多值路径，不能因为最后一段单选就变成 DIRECT。静态多值路径本次碰巧只有一人时也不自动改变分配模式。应由服务端计算 `multiple`，前端仅作展示与及时提示。

### 4.5 图读取复用边界

复用现有投影读取、发布路径编译和预算控制基础；新增面向人员路径的有限步求值入口，不直接套用通用关系图的所有行为：

- “用户 A → 部门 → 创建人 A”是合法结果。不能因再次出现用户 A 而报图循环；求值状态按“路径步骤 + 实体 + 记录”区分，固定步数保证终止。现有流程协调等图消费者的环检测规则保持各自语义。
- 人员解析不接受末层分页或截断结果，否则会遗漏候选人。保留最终最多 200 人的限制，并为每层记录数、总节点数和查询耗时设置明确预算；超限报错，不静默截取前 N 人。
- 增加服务端专用的流程人员解析授权入口，校验流程绑定、根记录与发布路径，只读取关系键和必要用户标识。后台执行不能依赖当前浏览器用户的可见范围，也不能向客户端暴露通用权限绕过开关。
- 设计期元数据查询及试算分别检查配置权限和数据查看权限；试算不能成为跨实体的任意记录读取接口。

### 4.6 空值与异常

- 中间关系为空：该分支无结果；其他合法分支可继续。最后全为空时进入现有空办理人策略。
- 用户删除或停用：按现有人员有效性规则处理并记录原因；不回退为另一位同名用户。
- 根记录缺失、悬空关系、路径不合法、身份歧义、超限：返回可区分的错误码和失败步骤，不作为成功的部分人员结果。
- 数据库异常、超时等基础设施问题不能伪装为空人员，保持失败并进入现有异常处理链路。
- 已删除/失效的中间记录与“关系字段本来未填”区分记录，便于运维定位。

## 5. 部门创建人补齐

针对系统部门，新增 `sys_organization.create_by`，存创建人的 sys_user 主键，登记为只读用户关系。

- 新增组织/部门时，由服务端从可信操作上下文写入，普通客户端不能伪造或修改。
- 覆盖管理页面、接口、组织导入及系统初始化等创建入口；无可识别自然人身份的系统创建记录允许为空，不捏造创建人。
- 历史部门没有可靠创建记录时保持为空；只有有可靠审计依据才能回填，不能默认填管理员或负责人。
- 历史部门创建人为空时，路径正常返回空人员，并按现有空办理人策略处理。
- 若业务里的“部门”是自定义实体且已经有用户类型创建人字段，可以直接复用该字段，无需给它重复加列。

## 6. 建议实施顺序

1. **元数据与字段基础**：统一可遍历关系描述，补齐系统部门创建人及写入入口，明确历史字段身份存储语义。
2. **后端闭环**：V2 参数、路径校验/编译、发布产物、批量解析、分配模式和错误码；先用服务测试打通示例。
3. **前端配置**：关系路径选择器、单/多值提示、失效路径回显、V1/V2 load-save，以及切换多人办理时的保存逻辑。
4. **全链路适配**：下一审批人候选范围与预览、多实例入口、扩展目录 schema、流程配置导入导出及引用依赖。
5. **验收**：新能力与原 V1 流程一起回归。知会等当前独立人员字段配置若需要支持路径，复用同一组件与端口并明确纳入后续范围，避免声称自然生效。

关键验收用例：

- 原直接单选/多选用户配置运行和回显不变。
- “申请用户 → 所属部门 → 创建人”正确解析；申请用户本人也是部门创建人时仍成功。
- 停在用户节点与继续展开用户节点都能保存、回显。
- 动态实体、系统实体混合路径，以及显式一对多关系可执行。
- 中间多值、末端单值，多个分支命中同一用户时正确去重，普通任务保持候选人模式。
- 空部门、历史部门创建人为空、删除/停用用户、悬空关系均得到明确结果。
- 未发布字段、非用户终点、伪造目标、身份冲突、超过深度或人数上限时拒绝。
- 普通用户发起流程、后台执行和下一审批人预览的业务解析语义一致；预览遵循权限。
- 重发布实体不改变旧流程的结构解释；节点创建前关系数据更新可生效。
- 导入导出跨环境重新映射完整路径并校验依赖，不能只处理第一段。

## 7. Flyway 与本次交付

本次实现已包含：关系元数据目录、人员路径 V2、发布版本钉定、有限步批量解析、部门创建人、节点配置与下一审批人路径选择、逐段迁移依赖和旧配置兼容。

- 关系类型：`REFERENCE_FIELD`、`SYSTEM_REFERENCE`、`RELATION`；显式父子关系同时提供 `PARENT_RELATION` 返回所属记录。受控配置另支持 `REVERSE_REFERENCE`。
