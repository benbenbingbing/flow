# wfpack 七个未拒绝反例：影响与修复建议

日期：2026-11-11。对应 [多轮测试报告](wfpack-negative-matrix-2026-11-11.md) 中的 S08、S09、S13、S15、S16、S18、S23。本次复核已有响应、复现包和当前源码，未启动新一轮实机测试，也未修改导入行为。

**后续状态：已按本评估完成修复。** 七个反例的 42 次实机上传均被拒绝，完整迁移模块 317 项通过，见 [修复及回归报告](wfpack-semantic-validation-fix-2026-11-11.md)。以下保留修复前的评估依据与建议。

## 建议结论

**建议全部补齐校验；前六个用例对应的四类问题按 P2 安排在近期版本修复，最后一个依赖清单格式问题可按 P3 随同处理。** 处理顺序建议：快照版本一致性 → 未知选择范围 → 非正源版本 → 包编号 → 附加依赖清单格式。

这七个是失败用例数量，实际只有五类校验缺口：0 和负版本共享根因，缺失和空包编号也共享根因。没有新增证据表明它们属于已发生配置损坏的 P1 阻塞问题。

## 复现条件与证据边界

七个用例均从有效合成包修改指定内容，并重新计算校验和；跨环境签名不匹配按现有流程由管理员确认该文件 SHA256 后继续。它们揭示的是内容语义校验不足。未同步校验和的正文篡改、未确认来源及确认值不匹配，已由其他反例验证拒绝。

七个用例都在已有一致业务配置的目标环境执行，最终 `blocked=false`、批次 `PUBLISHED`、条目 `SUCCESS`，目标资产发布前后版本和哈希相同，`unchangedConfig=true`。

这里“业务配置未变化”是指测试指纹覆盖的流程、实体、表单、节点、迁移资产及物理业务表清单。**导入批次、条目和迁移基线属于迁移元数据，不在该指纹的全部覆盖范围内。** 当前实现对一致复用项同样执行 `markPublished` 并写迁移基线，因此不能理解成“没有任何数据库写入”。也不能据这些一致配置场景断言，非法包在全新或需要升级的目标上同样没有影响。

原始结果见 [matrix-final.json](evidence/wfpack-negative-2026-11-11/matrix-final.json)；下面每项均附对应复现包。

## 七项详细说明

### 1. S08：源资产版本为 0 仍接受

- **复现**：把清单首个实体资产 `mx_entity` 的 `sourceVersion` 从正常值改为 `0`，正文不变。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S08.wfpack)。
- **实际结果**：上传条目记录源版本为 0；分析为 `CONSISTENT`；发布返回 `SUCCESS`。目标实体版本仍为 2，前后哈希一致。
- **原因**：解包只使用 `Integer.parseInt`，没有正数范围校验；比较时内容一致会先返回 `CONSISTENT`。
- **影响**：接受了不符合正常发布版本含义的元数据。源码显示一致复用也会把条目源版本写入迁移基线，存在把 0 写入基线的路径。尚未证实因此发生错误降级，不能把它等同于已经绕过降级保护。
- **建议**：需要修，P2。上传解包阶段要求 `sourceVersion` 为受支持范围内的正整数，不能自动改成 1，否则会制造错误的来源历史。

### 2. S09：源资产版本为负数仍接受

- **复现**：同一字段改为 `-1`，正文不变。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S09.wfpack)。
- **实际结果**：源版本 -1 被保存，分析为 `CONSISTENT`，发布成功；目标实体仍为版本 2，前后哈希一致。
- **原因与影响**：与 S08 同根因，负数同样会进入导入历史，并存在进入迁移基线的代码路径。主要风险是源版本语义和后续追溯被污染；本例未出现业务配置覆盖。
- **建议**：需要修，P2，与 S08 使用同一条范围校验。回归需覆盖负数、0、缺失、null、非整数和越界值，以及正常正版本导入。

### 3. S13：清单声明不支持的快照版本，仍继续导入

- **复现**：只把资产清单的 `snapshotSchemaVersion` 改为 `999`，正文的 `schemaVersion` 仍为 `3`。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S13.wfpack)。
- **实际结果**：上传、分析、发布均成功；目标配置未变化。
- **原因**：解包检查了包的 `formatVersion`，但没有检查资产清单中的快照版本，也没有核对清单版本与正文版本是否一致。包格式版本与快照版本是两个层次，应分别校验。
- **影响**：导入器接受了自相矛盾的协议声明。后续快照协议升级时，存在旧导入器按已有字段读取、遗漏新语义的兼容性风险。这是源码推断的风险；本例仅证实“清单 999、正文 3”未拒绝，未实测真正未来版本正文的行为。
- **建议**：需要修，P2，优先处理。按包格式和资产类型维护明确支持的快照版本集合，同时校验清单与正文一致；不支持时在上传阶段明确提示版本不兼容。补测前需确认现有受支持历史包，避免误伤兼容性。

### 4. S15：缺失包编号，被转换为字符串 `"null"`

- **复现**：从 `manifest.json` 删除 `packageNo` 字段。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S15.wfpack)。
- **实际结果**：响应中的包编号为字符串 `"null"`，不是 JSON null；仍创建批次并发布成功。
- **原因**：`String.valueOf(manifest.get("packageNo"))` 把缺失值转换成了普通字符串，后续未做必填校验。
- **影响**：不同异常包可能都显示为 `null`，影响按包编号进行人工核对、审计和沟通。现有上传去重依据文件 SHA256，回滚定位使用导入批次 ID，不能据此断言发生批次混淆或回滚错包。
- **建议**：需要修，P2。先验证原始字段存在、类型为字符串、内容非空，再使用该值；不要生成临时源包编号掩盖源文件缺失。字段长度和合法格式按现有导出协议及数据库字段约束确定。

### 5. S16：包编号为空字符串仍接受

- **复现**：保留 `packageNo`，值设为 `""`。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S16.wfpack)。
- **实际结果**：空编号进入批次记录，分析及发布成功。
- **原因与影响**：与 S15 同属包身份字段校验不足。列表或日志不能展示有效源包编号，影响追溯；尚无证据表明破坏业务配置或文件摘要去重。
- **建议**：需要修，P2，与 S15 一起处理。校验需覆盖缺失、null、空字符串、纯空白、错误类型和超长值，保留合法历史编号的兼容性。

### 6. S18：选择不存在的配置分区，仍提示发布成功

- **复现**：把实体资产选择范围改为 `{"full":false,"sections":["UNKNOWN"]}`。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S18.wfpack)。
- **实际结果**：分析不阻断，返回 `CONSISTENT`，最终 `PUBLISHED`，目标配置未发生变化。
- **原因**：`normalizeSelection` 检查“至少有一个分区”以及 `formKeys/listKeys` 的关联条件，但不检查分区名称是否受当前资产类型和协议支持。选择裁剪会保留身份等支持信息，而未知名称没有对应配置部分可以应用。
- **影响**：用户或外部制包工具拼错分区名称时，系统可能遗漏其本来期望迁移的配置却显示成功。跨版本增加新分区时也会产生“旧导入器没有处理但未告知”的风险。本例未证明会误删目标配置。
- **建议**：需要修，P2，优先处理。按资产类型和协议版本验证分区白名单；未知名称明确拒绝，列出可选值；合法名称与未知名称混用也应拒绝，不能静默丢掉未知项或退回全量导入。回归同时覆盖流程、实体及现有扩展分区。

### 7. S23：附加依赖清单损坏仍接受

- **复现**：把根目录 `dependencies.json` 改为非法 JSON 文本 `{broken`，同步更新校验和，资产快照中的依赖不变。[复现包](evidence/wfpack-negative-2026-11-11/fixtures/S23.wfpack)。
- **实际结果**：文件完整性检查通过，分析和发布均成功。
- **原因**：当前解包器生成该附加清单，但导入时不解析其 JSON；真正交给依赖解析器的是各资产快照中的 `dependencies`。
- **影响**：包内有损坏文件却被视为有效，影响人工检查和其他读取该文件的工具。当前证据没有发现必需依赖校验被绕过；不能据这个用例描述为“依赖缺失仍可发布”。
- **建议**：建议修，P3，可后排。最小改动是验证该文件能解析成预期的依赖数组及合法条目，并在格式错误时拒绝；依赖应用仍以已有资产快照为准。若还要做汇总清单与快照依赖的语义一致性校验，需先定义去重和局部导出规则，避免简单逐字节比较导致合法包误拒绝。

## 建议实现与验收范围

建议在 `ConfigMigrationPackageCodec.decode` 中、创建导入批次之前集中补齐上述检查。这样可以在上传阶段给出明确错误，避免非法元数据先进入批次、后到发布阶段才暴露。

| 检查项 | 修复后的验收要求 |
| --- | --- |
| 七个既有反例 | 同一复现文件被明确拒绝，不新增导入批次、条目或迁移基线，业务配置不变 |
| 错误信息 | 指明字段/资产/文件及原因，不暴露内部异常；版本不支持与文件格式错误能区分 |
| 正常兼容性 | 当前完整包、局部包及已明确支持的历史格式样本仍可导入 |
| 非一致目标 | 在全新目标和需要升级的目标重放相同反例，均在应用前拒绝 |
| 依赖保护 | 损坏附加清单拒绝；正常附加清单下，快照必需依赖缺失仍阻断 |
| 历史记录 | 修复后先只读盘点已有异常元数据；本次不自动改版本、编号或删除历史批次 |

- [ConfigMigrationPackageCodec.java](../../workflow-server/workflow-migration/src/main/java/com/workflow/migration/application/ConfigMigrationPackageCodec.java)：解包、版本读取、选择范围规范化、包编号转换、依赖来源。
- [ConfigMigrationPackageService.java](../../workflow-server/workflow-migration/src/main/java/com/workflow/migration/application/ConfigMigrationPackageService.java)：上传按摘要去重、条目入库、一致性比较及源版本倒退保护。
- [ConfigMigrationImportApplyService.java](../../workflow-server/workflow-migration/src/main/java/com/workflow/migration/application/ConfigMigrationImportApplyService.java)：一致项也标记成功并更新迁移基线。
- [round3_final.py](evidence/wfpack-negative-2026-11-11/scripts/round3_final.py)、[harness.py](evidence/wfpack-negative-2026-11-11/scripts/harness.py)：反例变更、拒绝断言与业务配置指纹的具体范围。
