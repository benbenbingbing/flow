# 表单取消版本与全局发布方案

日期：2026-10-08。本文为已确认的方案与修改清单；代码实施和兼容边界见 [实施记录](form-global-publish-without-versions-implementation.md)。本机已执行 V112，V113 首次执行失败；修复后的迁移已通过只读预演、本机数据副本完整迁移及后端启动健康检查。用户自行处理 Flyway 失败记录，正常重启时重新构建并执行修复后的迁移。

## 1. 目标与业务规则

实体中的表单设置改为「编辑草稿 → 保存 → 发布 → 全局生效」。每张表单只有一份当前已发布配置，运行时按稳定的 `formId` 获取配置，不再生成、选择或固定表单版本。

| 操作或场景 | 目标行为 |
| --- | --- |
| 保存草稿 | 只保存设计修改，线上继续使用当前已发布配置 |
| 发布 | 完整校验草稿后原子替换当前已发布配置，发布成功后新进入的请求读取新配置 |
| 新增数据、发起流程 | 使用当前已发布表单，无需因表单修改而重新发布流程 |
| 运行中流程、待办办理 | 根据所属流程原有的表单 ID，读取该表单当前已发布配置 |
| 已结束流程、历史详情 | 同样使用当前已发布配置展示已有业务数据 |
| 子表单 | 只绑定子表单 ID，子表单发布后所有引用入口使用其最新已发布配置 |
| 列表按钮、关联内容、嵌入页面 | 只引用表单 ID，运行时动态解析当前已发布表单 |
| 撤销未发布修改 | 从当前已发布配置恢复草稿 |
| 未发布的表单 | 正式运行入口提示「表单尚未发布」，设计器预览可以读取草稿 |

取消表单版本号、版本列表、历史版本激活、按版本恢复、普通发布/热修复选择、热修复目标与补丁、热修复观察及专用回滚。

保留草稿编辑并发控制 `revision`、内容摘要和发布人/发布时间。它们用于防止覆盖他人的修改、识别配置变化和审计，不构成可选择或固定的业务版本。

本次范围是表单配置版本。实体业务数据版本、实体结构发布、Flowable 流程版本、组件/扩展制品版本、列表自身版本及嵌入页面自身版本继续按原有职责工作。其中涉及表单的固定引用必须改造。例如，列表自身仍可保留发布快照，但快照里的「打开表单」只保留表单 ID。

全局生效作用于同一个表单 ID 的所有引用。流程旧版本仍保留原来的节点与表单 ID 映射；单独发布表单不会把历史流程改绑到流程草稿新选的另一张表单，也不会改动 BPMN、办理人或业务数据。

## 2. 当前代码中的耦合

| 当前实现 | 已确认的行为 | 改造方向 |
| --- | --- | --- |
| `UiConfigReleaseService.publishStandard()` | 递增版本、创建发布记录、切换 ACTIVE | 表单发布改为覆盖唯一已发布配置 |
| `UiConfigReleaseService.publishHotfix()` | 生成补丁及按流程版本区分的有效目标快照 | 退出表单发布链路，移除热修复机制 |
| `EntityForm` | 包含 `activeReleaseId`、运行时基础版本、有效版本及热修复标志 | 清除表单发布版本字段，保留草稿修订与运行上下文 |
| `ProcessPublishHistoryService.prepareNodeFormsSnapshot()` | 把 `formReleaseId/formReleaseVersion` 写入流程节点快照 | 保留表单 ID、节点 ID、只读属性和顺序，不再写表单发布坐标 |
| `EntityFormRuntimeService.resolveByBinding()` | 读取流程固定版本，部分场景应用热修复 | 无论新增、活动任务还是历史详情，均按表单 ID 读取当前发布配置 |
| `requireCurrentBindingForNewData()` | 表单新发布后要求重新发布流程 | 删除表单版本过期判断，保留存在性、已发布状态和实体归属检查 |
| 子表单设计与参数契约校验 | 强制保存 `childFormReleaseId/childFormReleaseVersion` | 保留子表单 ID，改为校验当前发布配置与参数映射 |
| 列表、关联内容、Embed | 包含目标表单固定发布坐标与签名验证 | 动态解析表单，重新建立与当前配置匹配的可信授权上下文 |
| `PublishedFormSubmissionService`、唯一性校验 | 前置处理与事务终检通过基础/有效发布身份复用规则 | 单次请求使用同一份已解析配置及内容摘要 |
| `ConfigMigrationSubFormReferences` | 随迁移包携带并匹配固定子表单版本 | 改用实体编码 + 表单键定位依赖，导入当前配置 |

当前 `resolveRuntimeFormRelease(formId)` 在没有发布记录时存在读取草稿的回退。取消版本时应一并收紧，否则正式入口可能使尚未发布的设计修改生效。

## 3. 数据模型与发布服务

### 3.1 建议新增独立的当前发布表

建议新增 `entity_form_published`，以 `form_id` 为主键，每张表单最多一行。表单发布从通用的多版本发布服务中分离，避免改动列表等对象的发布语义。

| 字段 | 用途 |
| --- | --- |
| `form_id` | 稳定表单身份，也是当前发布配置唯一键 |
| `entity_id` | 检查实体归属与查询默认表单 |
| `snapshot_document` | 当前完整发布配置：表单元数据、节点、字段投影、按钮、事件绑定、校验、数据源和关联内容 |
| `content_hash` | 校验内容完整性、判断是否有变化、防止旧页面按错误配置提交 |
| `published_by`、`published_at` | 显示最近一次发布信息与审计 |

不设置 `version`、`release_mode`、`base_release_id`、`hotfix_target_id` 或历史 ACTIVE 状态。

快照 JSON 的 `schemaVersion` 如仍需要，可以保留：它表示序列化格式，与用户可选择的表单配置版本用途不同。组件、接口制品依赖也继续携带其必要的制品身份。

默认表单、启用状态等影响运行入口选择的属性应以发布态为准，不能通过读取草稿元数据使「保存」提前改变运行行为。发布默认表单变更时，在实体范围内保证默认选择唯一且原子切换。

发布操作写入现有通用审计体系，记录操作人、时间、说明和变更摘要。审计记录不参与配置选择或运行时解析。旧版本数据可以先只读归档，新机制不再持续创建可执行的表单历史版本。

### 3.2 推荐服务边界

新增 `EntityFormPublishService` 和统一的当前发布读取入口，承担表单发布、当前配置查询、草稿差异、撤销未发布修改。命名为建议，实施时可按项目结构调整。

发布过程：

1. 校验发布权限，锁定草稿所属表单；涉及默认表单切换时同时建立实体范围的并发边界。
2. 检查预检时的草稿修订号/哈希和当前已发布哈希，避免发布已被其他人改动的内容。
3. 复用现有完整性校验，构建包含节点、事件、按钮、关联内容等的完整快照。
4. 校验所有子表单存在且已发布，检查循环引用、嵌套深度、参数和实体关系；也校验引用当前表单的已发布父表单是否仍兼容。
5. 在同一事务内覆盖当前发布行并写审计；配置相同时按无变更处理，无需制造新发布身份。
6. 发布成功后运行入口使用当前配置；发布失败时原发布配置继续可用。

保留业务校验与正常发布权限。原来为 HOTFIX 准备的目标集合、补丁兼容性分级、观察窗口及专用回滚退出发布流程。

### 3.3 运行接口

表单接口收敛为当前配置查询、发布预检、发布、草稿差异、撤销未发布修改。例如当前配置可用 `GET /api/entity-forms/{id}/runtime`，最终路由结合现有调用方统一调整。

返回 `formId`、渲染配置、`contentHash` 和可信运行上下文令牌。删除表单 `releaseId/releaseVersion/effectiveReleaseId/hotfixApplied`，调用方不再提交用于选择历史配置的发布坐标。

表单版本列表、版本摘要、历史激活、恢复历史草稿、热修复发布和回滚端点退役。通用控制器中的列表接口应保留其现有行为。

## 4. 「立即全局生效」的执行边界

### 4.1 服务端与已有页面

以发布事务提交为生效点，发布成功后新进入的运行请求统一读取当前配置。已受理的单次请求使用受理时解析出的同一份配置完成默认值、事件、校验和写入，避免处理中途切换规则或重复执行外部接口。

浏览器已经渲染的页面不会仅因服务器发布而自动重绘。建议按以下规则处理：

- 重新打开、刷新或页面重新获得焦点时检查当前配置摘要；无编辑内容的页面可直接刷新配置。
- 已有填写内容时保留数据，提示表单已更新，重新加载配置后按仍存在的字段映射草稿；移除或无法映射的字段明确提示用户核对。
- 提交或执行按钮前，服务端检查页面摘要与当前配置是否一致；变化时返回稳定的 `FORM_CONFIGURATION_CHANGED`，在副作用发生前要求核对新配置。
- 历史详情使用最新布局展示历史业务数据。新增必填字段不会在只读浏览时触发写入校验；删除显示节点也不删除既有业务数据。

以上保证旧页面不能继续选择旧配置执行。如果要求所有已打开页面在发布瞬间主动收到提示，还需要增加配置变化推送能力；将其与服务端全局生效区分验收。

### 4.2 嵌套配置与缓存

根表单不再保存子表单快照版本，而是按 ID 动态读取子表单当前配置。子表单发布可能改变参数契约，因此预检必须检查当前已发布父表单的输入映射、输出映射和节点引用；无法兼容时返回具体引用位置。

单次请求应解析并复用整张依赖图，记录根表单及所用子表单的摘要。只检查根表单哈希不足以识别「根表单没改、子表单已经更新」的情况。

初期建议当前发布定位直接读数据库，避免依赖单机缓存或 TTL 形成发布延迟。确需缓存时，必须验证当前摘要后才能复用缓存内容，并覆盖多实例节点、子表单及列表/关联内容目标表单的缓存路径。

## 5. 不能随版本字段直接删除的机制

### 5.1 运行上下文鉴权

`UiReleaseResolutionTokenService` 当前既固定发布身份，也约束用户、任务、流程实例、记录、父子引用及嵌入会话。取消版本后应将表单部分改为运行上下文授权，保留这些权限边界和到期时间。

令牌绑定表单 ID 与当前内容摘要/依赖图摘要，不能允许客户端凭一个 formId 执行任意任务的审批按钮、读取其他记录或调用未绑定接口。子表单派生授权必须根据父表单当前发布引用检查，而不是只验证目标表单存在。

共享令牌服务还有列表、Embed 等调用，不能整体删除。新表单令牌格式与旧格式需明确区分；上线时旧令牌失效并重新鉴权，客户端保留填写内容后重载上下文。

### 5.2 提交、事件与幂等

调整 `PublishedFormSubmissionService`、`NodeFormSubmissionService`、事件执行、按钮动作和实体写入终检，让它们复用服务端解析出的配置对象，或校验同一内容摘要。

幂等键目前部分包含发布 ID。改造后应使用业务提交追踪键、动作、绑定稳定 ID、绑定配置指纹和输入指纹等材料，保证同一受理请求重试不会重复执行，新的配置操作也不会误用旧响应。

审批权限、只读限制、任务有效状态、记录归属、实体字段校验和跨字段校验都需保留。

### 5.3 表单唯一性

当前 `entity_form_unique_claim.constraint_key` 使用发布/热修复快照身份区分规则条件变化，不能简单删除命名空间中的这一段。

建议使用 `formId + ruleId + 规则语义指纹` 区分占位。规则指纹覆盖字段、条件、空值策略和规范化规则，避免条件变更后的旧占位造成假冲突；单纯布局修改不应改变唯一规则占位身份。

保留跨表单共用的 `entity_form_unique_value_gate` 加锁及业务数据复查，继续阻止并发同值写入。旧占位需按新语义迁移、重建或明确退出判断，并验证修改自身记录时不会冲突。

### 5.4 删除与引用保护

过去历史发布快照可能在草稿被删除后继续工作；改为按表单 ID 解析后，这一依赖不再成立。删除保护必须按稳定表单引用检查流程发布绑定、子表单、已发布列表按钮、关联内容和 Embed 配置，不能只检查版本引用或草稿引用。

仍被需要展示或办理的流程及页面引用的表单不得直接删除。接口/组件的引用保护也改为检查当前已发布表单内容及实际仍可执行的其他制品；只读归档的旧表单版本不应再作为运行引用来源。

## 7. 数据库与旧数据迁移

本地已检查 SQL 与 Java 两类 Flyway 迁移，当前最大版本为 `V111`。实施时必须再次检查；若无新增占用，首个新增迁移可从 `V112` 开始。本文未创建迁移文件。

建议分为「新增并迁移当前配置 → 切换全部运行入口 → 清理旧结构」，可在同一个功能交付中完成，但 SQL 与代码部署顺序必须明确。破坏性清理要在旧代码已退出运行后进行。

1. 新增当前发布表。从每张表单的当前 ACTIVE 发布记录复制完整快照，不读取或发布未发布草稿。当前 HOTFIX 发布记录保存的是完整草稿发布文档，可作为统一当前配置的迁移候选；迁移时重新检查 JSON 完整性、依赖及内容摘要。
2. 旧热修复按不同流程版本产生的有效快照可能不同。全局模型明确收敛为该表单唯一当前发布配置，迁移前列出与旧目标的差异；不能把任意一个流程目标快照当作全局配置，也不能合并不同目标产生的新配置。
3. 无 ACTIVE 但仍有可执行历史引用的表单必须列为迁移异常，不能默默启用草稿；重复 ACTIVE、引用已删除表单、目标缺失或循环引用也必须输出具体对象。V034 清空发布记录和依赖索引后留下的失效历史坐标可以保留并报告警告：仅限表单未删除、无当前发布指针、无任何发布记录且历史 pin 不存在的情况。此类表单仍未发布，相关流程在管理员重新发布该 formId 前返回 `FORM_NOT_PUBLISHED`；迁移不激活草稿或重写历史。
4. 新运行解析器兼容读取旧流程 JSON 中额外的 formRelease 字段，但只用其中的稳定 formId。不为此次改造重新部署历史流程，也不批量重写不可变流程历史来改变节点绑定。
5. 清理草稿节点、当前发布文档、列表目标参数、关联内容和 Embed 配置中不再使用的表单发布坐标。旧只读历史可以保留原文，但不得再成为可执行版本来源。
6. `process_ui_release_binding` 的表单用途改为稳定引用绑定；若继续作为引用/影响索引，可迁移为不包含 pinned_release 字段的结构。不能未检查其他用途就整体删除。
7. 更新 `entity_form_unique_claim` 的占位身份及必填发布字段；保留 value gate 和并发复查。更新 `embed_view_release` 中表单固定发布字段与相关 CHECK 约束，并核对会话文档和回执中的旧坐标。
8. 切换后 `ui_config_release` 不再新增 FORM 版本；它仍服务 LIST 等对象，不能整体删表。V113 归档旧 FORM 发布；用户确认清理后由 V114 删除旧 FORM 发布记录，独立审计继续保留。
9. `ui_config_hotfix_target`、`ui_config_hotfix_request`、`ui_hotfix_observation_metric` 及相关权限停止新写入；已核实没有需要保留的运行用途，V114 按指标、申请、目标顺序删除三表，并清除热修复权限；列表历史查询不再关联三表。
10. 前后端、移动端和 Embed 同步发布新协议；旧令牌失效后保留填写内容并重新加载，避免新旧节点继续执行不同配置规则。

不得修改、删除或重命名主分支已有的 `V*__*.sql`，不得同步修改 `V001__business_schema.sql`，不需要建立新 baseline。正常升级不执行 `flyway repair`；本机 V113 首次失败留下 `success=0` 记录时，必须先校验其他历史迁移、确认没有部分写入，并按 AGENTS.md 获得明确确认后才清理失败记录和重试。结构清理和数据迁移通过更高版本新增迁移完成，最终实施交付必须逐一列出新增、修改或删除的迁移文件。

## 8. 推荐实施顺序

1. **当前配置底座**：新增发布表与表单发布/读取服务，迁移当前配置，明确接口字段和请求内一致性边界。
2. **服务端完整切换**：流程、子表单、列表按钮、关联内容、Embed、提交、事件、唯一性及运行令牌全部切换；兼容旧流程 JSON 中稳定表单引用。
3. **前端完整切换**：表单设置、设计器、发布弹窗、Web/移动端/Embed 统一使用新协议，保留草稿与旧页面填写内容。
4. **周边收尾**：迁移包、权限、审计、引用保护、文档和测试同步更新；停用并清理旧版本/热修复链路。

运行入口切换必须作为完整交付验收，避免出现部分入口读取当前配置、另一部分仍固定旧版本的长期混合状态。

## 9. 验收重点

- 保存布局、按钮、校验和事件草稿后，所有正式入口仍使用原已发布配置。
- 发布一次后，新增数据、新流程、现有待办和已结束流程详情都使用当前配置，流程不必重新发布。
- 子表单单独发布后，父表单、历史已发布列表按钮、关联内容及已有 Embed 配置能解析到最新表单；不兼容的父子参数引用在发布前明确定位。
- 页面填写期间发生发布，数据不被自动清空；旧摘要的写请求在副作用前得到更新提示，重载后按最新规则提交。
- 多实例服务节点在发布成功后新进入的请求读取相同当前配置；根表单未改而子表单变化也能被识别。
- 单次提交的默认值、事件、接口调用、必填/跨字段校验、唯一性和事务终检使用同一配置；重试不重复执行接口。
- 唯一规则改变条件、只改布局、编辑自身记录及跨表单并发同值写入均符合预期。
- 历史业务数据继续可读，不因隐藏字段或新增必填项在浏览时被改写。
- 任务、记录、父子引用及 Embed 鉴权仍有效；客户端不能通过旧 release 参数或旧令牌执行历史事件链。
- 老数据库升级和空数据库按全部 Flyway 迁移顺序初始化都通过；异常旧引用能定位，旧流程 JSON 可读取，迁移包往返正确。
- 设置页不再展示表单版本及热修复，列表等保留范围内的发布功能正常，Git 差异没有修改已有不可变迁移。

实施验证应调整现有发布、流程节点、提交、令牌、唯一性、迁移与 Embed 测试，补充全局生效的行为用例。当前仅完成代码梳理和方案文档，不据此声称业务测试已通过。
